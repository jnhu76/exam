# Exam v0.0.2

## Why this release exists

`v0.0.2` is the first release whose tag maps to a **published prebuilt
image** (`ghcr.io/jnhu76/exam:v0.0.2` + `sha-<commit>` alias; `v0.0.1`
predates the image workflow). It also closes the S1 delivery/recovery
evidence gaps: real process-boundary restart proof, a PR-blocking
fresh-install acceptance gate, and productized operator upgrade/uninstall
lifecycle guides. An operator can now obtain, upgrade, roll back, and
remove the deployment entirely from documentation alone.

## Problems solved

- Real restart/deadline behavior previously relied on in-process evidence;
  the API is now driven as a real child process across SIGKILL, proving
  deadline durability, scanner convergence, and disruption recovery across
  the process boundary (#326).
- Fresh installs drifted from the production Compose topology; every PR now
  runs a disposable fresh-install gate (env-authority, compose smoke,
  persistence across recreation, residue assertions) (#327).
- Operators could only run the stack from a source build; `docker-compose.yml`
  now pins a prebuilt semantic image (`EXAM_IMAGE` derived from
  `.release-version`), published by the release workflow with an immutable
  git tag and no `latest` convenience tag (#321 implementation).
- Upgrade and uninstall existed only implicitly; a canonical lifecycle guide
  (upgrade path, version-skipping policy, forward-only rollback contract,
  preserve vs. full-removal uninstall) plus an executable suite now cover
  them (#329).
- Logged-out or password-changed sessions stayed valid until expiry; a
  durable per-user credential epoch now revokes them (#325).

## Notable changes

### Added

- Prebuilt image distribution: release workflow publishes
  `ghcr.io/jnhu76/exam:vX.Y.Z` (raw `type` passthrough of
  `.release-version`) plus a `sha-<short>` alias from the exact release
  commit; OCI `revision`/`created` labels carry the source SHA; explicit
  `latest=false` (upstream `latest=auto` would add one for stable semver).
- `generate-env` derives the operator `EXAM_IMAGE` pin from
  `.release-version`; canonical pins follow the release authority on
  re-runs (the upgrade path), explicit mirror values win (offline
  `docker save`/`docker load` transfers).
- `docker-compose.yml` operator path consumes the prebuilt pin on `app`
  and `email-worker`; `docker-compose.build.yml` is the sole source-build
  surface for contributors/PR acceptance (all deployment suites merge it).
- Operator upgrade & uninstall lifecycle guide
  (`docs/deployment/upgrade-and-uninstall.md`) + executable suite
  (`pnpm test:deployment:upgrade`).
- PR-blocking fresh-install acceptance gate (`deployment-fresh-install` CI
  job) with env-file authority checksum/canary mechanics.
- Real process-boundary restart/deadline evidence suite
  (`apps/api/src/runtime/processRestartDeadline.process.test.ts`).

### Changed

- Operator start is `up -d` (no local build); the runbook, gates doc,
  and topology contract enforce the two-path split.
- Runbook shutdown section: `down -v` no longer claims to destroy data
  (bind mounts only since P7-C1); deletion is the explicit `rm` in the
  lifecycle guide.

### Fixed

- Authentication tokens remained valid after logout/password change —
  durable per-user auth epoch now revokes them (#325).
- Release tag derivation would have published a `v`-less tag (metadata
  semver `{{version}}` strips the prefix — never matching the operator
  pin) and an unintended `latest` tag; both traps were pinned with
  `type=raw` + `flavor: latest=false`, verified against upstream source.
- Lifecycle-suite credential probe could false-pass on a CSRF-403 origin
  rejection; it now sends the stack's allowed origin and asserts a real
  `401` auth rejection.

### Security

- Logout and password changes revoke previously issued authentication
  tokens (#325).

### Deployment / operations

- Upgrade path: `git pull` → `node scripts/generate-env.mjs` (re-pin) →
  `docker compose --env-file .env.deploy pull` → `up -d`; migrations run
  automatically on app start (journal applies backlog in order, idempotent
  reruns, worker serialized behind app health).
- Version-skipping policy: intermediate releases may be skipped by
  default; release notes must announce required intermediates and `db`
  image major bumps (breaking).
- Rollback: restore the pre-upgrade backup + redeploy the previous image
  tag (forward-only migrations; canonical pins follow
  `.release-version`, so edit `.env.deploy` after the last
  `generate-env` run or pin by digest).
- Uninstall: preserve mode (`down`) vs. full removal (`down` + delete
  `EXAM_DATA_ROOT` + delete `.env.deploy`); the data root and env file
  are coupled (regenerated secrets against kept PGDATA break the stack).
- First GHCR publish is PRIVATE by default (public repo does not imply
  public package): the one-time Package-settings flip to Public and the
  anonymous-pull verification are part of this release's publication
  closeout.

### Internal / infrastructure

- Deployment topology contract now also guards the lifecycle doc against
  operator-command drift (canonical invocation tokens must stay; any
  `up --build` operator form must not return).
- Contract guards for the fresh-install gate (env authority, canary port,
  residue) and the restart evidence harness (exit-promise settle-once,
  SIGKILL + pid-gone + ECONNREFUSED proofs).

## Known limitations

- Pre-1.0 development baseline; the generic product roadmap continues
  under Issue #333.
- Published images are linux/amd64 only; other architectures use the
  documented source-build path.
- Single-node single-tenant deployment is the only supported topology
  (multi-instance/tenant are later phases).
- The GHCR package needs the one-time Public flip documented above.

## Upgrade notes

No special upgrade action is required for `v0.0.1 → v0.0.2`: migrations
run automatically on app start; `generate-env` re-pins `EXAM_IMAGE` from
`.release-version` (or update a mirror value by hand); `up -d` recreates
`app`/`email-worker` from the new image while the `db` container and data
are untouched. Follow the lifecycle guide (`docs/deployment/upgrade-and-uninstall.md`),
including the mandatory pre-upgrade backup.
