# Exam v0.0.12

## Why this release exists

`v0.0.12` is the observability-evidence release: it makes failures of the exam
platform visible, correlatable, and trustworthy end-to-end, and it hardens the
identity and integrity of the evidence itself.

When an exam save fails, an operator previously had to reconstruct what
happened from three disconnected silos: client telemetry that could silently
duplicate or carry credential-shaped strings into the database, proctor
timelines that a single extreme client date could render unusable, and server
logs keyed by a request id that was ambiguous across process restarts and — in
production — taken from a client-controlled header. Background loops (business
failure scanners, client-event retention) could hang or throw persistently with
no escalation signal beyond per-pass ERROR lines. This release closes those
gaps as the first merged wave of the observability campaign
([#800](https://github.com/jnhu76/exam/issues/800)): frontend capture and
cross-layer correlation, a read-only investigation UI, diagnostics failure
counters, receipt and refusal evidence for answer saves, upload idempotency,
at-rest privacy minimization, temporal write/read integrity
([ADR-026](../adr/ADR-026-client-event-temporal-evidence-boundary.md)), and a
server-owned UUIDv4 request identity
([ADR-025](../adr/ADR-025-http-request-correlation-identity.md)).

It also lands the tick-failure escalation decision
([ADR-024](../adr/ADR-024-tick-level-throw-escalation.md), accepted after two
independent adversarial reviews): persistent tick-level throws in background
loops now escalate as `operability.tick_failure` alongside the
`operability.business_failure` signal for persistent business failures.

The release is based on the actual ancestry `v0.0.11`
(`5aa82f58945ed97c16b9d7ea66fb4e7eb34fa435`) → preparation base `master`
(`423f2945d9feef73a5413e498fb2772cc245c754`): 126 commits containing 31 merged
PRs (#850–#853, #859, #879–#881, #883, #884, #887–#896, #899, #902, #904,
#906, #909–#916); 30 arrived via merge commits and #899 via rebase merge (no
merge commit), so the range contains **no direct-to-master pushes**. The
release-preparation merge adds only the release-authority files plus the two
README badge lines the release workflow now enforces (#899).

## Problems solved

1. **Frontend failures never reached the telemetry pipeline (#854, PR #853).**
   Render crashes, unhandled errors and transport failures died in the
   browser. PR #853 wires them into the existing client-event pipeline
   (logger → buffer → shared sanitizer) with category identifiers and stable
   error codes only — no raw `message`, `stack`, `componentStack` or URL
   content is persisted — under finite vocabularies with three-way wire
   failure classification (#800).

2. **Exam-save faults could not be correlated across layers (#855, PR #850).**
   The same save fault produced unrelated records in client telemetry, the
   proctor timeline and server logs. PR #850 correlates them: the client save
   catch records machine facts (`errorCode`, `status`, `requestId`) from
   `ApiError` when present (true network failures stay `NETWORK`, never
   mislabeled), and the server side joins the same fault across surfaces.

3. **Investigation surfaces had no UI (#856, PRs #851, #880).** The read
   endpoints existed but were unreachable by admins. PR #851 adds the read-only
   telemetry investigation UI (timeline with >50-event paging, server receive
   time `serverRecordedAt`, precise filters, deep links), and PR #880 supplies
   the browser-level acceptance evidence (layout/overflow/interaction at 390px)
   the repository contract requires for visible UI claims.

4. **Diagnostics showed no failure counters or dead letters (#857, PR #852).**
   PR #852 projects cumulative failure counters, scanner failure diagnostics
   and dead-letter log visibility onto the existing read-only diagnostics
   surface, plus the measurement tooling to prove them.

5. **ACK loss duplicated low-trust telemetry (#863, PR #889).** When the
   client-events POST response was lost, the buffer resent the whole batch and
   every layer was append-only: no client key on the wire, pure INSERT in the
   repository, no unique constraint on the table. PR #889 adds a
   client-generated event key end-to-end (contracts → repository → web buffer)
   enforced by migration `0046` as a unique `(organization_id, user_id,
   event_id)` index; legacy rows and key-less senders stay outside the
   constraint (NULLs are distinct).

6. **client_events persisted credential shapes and raw query strings
   (#875, PR #888).** A key-name denylist could not see a JWT under an
   innocent key (`{ note: "<JWT>" }`), and the top-level `route` free string
   carried query strings (`?token=…`) into the database and the proctor
   timeline. PR #888 replaces denylist-by-key with credential-shape scanning
   of values under any key, structures the route field, and drops query
   strings, restoring the JWT/userinfo coverage without backtracking.

7. **One extreme client date poisoned the whole batch and the timeline
   (#903/#874, PRs #911, #904, ADR-026).** A schema-valid year-0000
   `occurredAt` reached PostgreSQL and failed the entire batch INSERT
   (`22008` → HTTP 500) with no isolation for the innocent peers; an
   already-stored extreme date made the attempt's investigation timeline
   unreadable. PR #911 rejects unrepresentable dates at the schema boundary
   with a standard 400 and teaches the client to classify transport outcomes
   and isolate only determinately-rejected events (poison-batch isolation);
   PR #904 projects the timeline's `occurredAt` as exact UTC text so no client
   date can break rendering. ADR-026 records the boundary decision
   (TIME_WINDOW_NO_GO: no server time-window admission test).

8. **Client-claimed metadata was displayed as verified fact (#901, PR #902).**
   The answer detail page and monitoring dialog mixed client-declared
   `requestId`/`status` with server facts with no labeling. PR #902 labels the
   whole client-event metadata group as client-claimed and unverified,
   separates "server received" from "client claimed" timestamps, adds source
   badges in the monitoring dialog, and adds the production boot guard: a
   forged request-id header can no longer control `request.id`.

9. **Request identity was ambiguous and client-influenced (#860, PR #912,
   ADR-025).** Fastify's default `req-<base36>` generator is only unique
   within one process, and production previously trusted a client-supplied
   request-id header. PR #912 adopts the Owner-superseding policy: a
   server-generated UUIDv4 per HTTP request (`genReqId: () => randomUUID()`,
   `requestIdHeader: false`, single production config entry), the same value
   in error envelopes and Pino `reqId`, with cross-process/restart uniqueness
   and envelope/log correspondence pinned by tests.

10. **System audit identity was written into the wrong key (#905, PR #906);
    import audit targets could name a non-entity (#908, PR #910); a declared
    404 degraded to 500 (#907, PR #909).** Background operations persisted
    their operation identity under `metadata.requestId` — an id no HTTP
    request ever had; PR #906 splits the identity keys at the writer boundary
    (`metadata.operationId` vs HTTP `metadata.requestId`) and refuses
    conflicting operation ids. The candidate-import audit target fell back to
    the HTTP request id when the import-log write failed; PR #910 makes it
    name a real entity. Role-assignment not-found routes sent a legacy flat
    payload the declared `ErrorResponseSchema` serializer rejects — turning
    every 404 into a 500; PR #909 restores the standard envelope.

11. **Persistent background failures threw with no escalation (#862, #885;
    PRs #884, #896, ADR-024).** Continuous business failures and tick-level
    throws (any non-DB root cause) surfaced only as per-pass ERROR logs —
    `docs/operations/active-alerting.md` §4 itself said "logs only". PR #884
    escalates persistent business failures as `operability.business_failure`
    (consecutive-failure-tick counters, freeze semantics, restart recovery
    pinned by tests); PR #896 adds `operability.tick_failure` for persistent
    tick-level throws per ADR-024 (accepted after independent adversarial
    reviews #897/#898), with the alert contract documented in
    `docs/operations/active-alerting.md`. PR #893 projects the
    `consecutiveFailedTicks` run-length counters into `/api/system/diagnostics`
    (#886), and PR #890 gives the client-event retention loop liveness/stall
    facts the same observability pattern (#871).

12. **Refused saves left no authoritative trace and UNKNOWN was undefined
    (#861, #867, PR #892); receipts were unreachable (#866, PR #891).** A
    refused answer save (`accepted: false`) produced no log line an operator
    could key by request id, and nothing codified what a *missing* server
    record proves. PR #892 emits exactly one structured WARN per refusal
    (`attemptId`, `questionId`, `clientSeq`, `reason`, `serverVersion`, with
    the envelope's `reqId`) and codifies the six-fact save-failure evidence
    model in `docs/operations/save-failure-evidence.md` — including the rule
    that a missing server record never proves the request never arrived.
    PR #891 adds the read-only receipt summary projection (count, max
    clientSeq, last savedAt) with route guards reconciled on both sides.

13. **Audit keyset pagination silently dropped rows (#877, PR #887).** The
    cursor carried timestamps at millisecond precision while the key is
    epoch-µs, so events sharing a truncated millisecond were skipped. PR #887
    moves the cursor to epoch-µs precision (cursor v3) and the client resets
    the cursor path on error retry instead of wedging.

14. **CI debt: artifact quota exhaustion (#894), unpinned-history docs fetch
    failures (#881), repeated coverage-lane races (#858, PR #859), and a
    release badge that could drift (#899).** CI now builds job-locally with
    no artifact fan-out; the docs build fetches pinned permalink commits
    explicitly with the job token; the #858 races were fixed at their proven
    layers (cold editor mount budget, timing layers) rather than by raising
    timeouts; and the release workflow now enforces README badge ↔
    `.release-version` agreement (#899, rebase-merged).

15. **Naming carried dead era vocabulary (PRs #915, #916).** Phase-era labels
    and RBAC-migration-era test-helper names were retired across production
    code, tests and tools so names match the current contracts.

## Notable changes

### Added

- Investigation surfaces (#800 first wave): frontend capture of boundary
  errors (category codes only, finite vocabularies), cross-layer save-fault
  correlation, the read-only telemetry investigation UI (paging,
  `serverRecordedAt`, filters, deep links), and failure/dead-letter counters
  on the diagnostics surface (PRs #850–#853, #880).
- Client-event upload idempotency with migration `0046` (PR #889).
- Escalation signals for background loops: `operability.business_failure`
  (PR #884) and `operability.tick_failure` (PR #896, ADR-024), with
  `consecutiveFailedTicks` in diagnostics (PR #893) and retention-loop
  liveness/stall facts (PR #890).
- Read-only answer-save receipt summary projection (PR #891).
- Production boot guard: client request-id headers cannot control
  `request.id` (PR #902).

### Changed

- Request identity is a server-generated UUIDv4 end-to-end (envelope + Pino
  `reqId`), single production config entry (PR #912, ADR-025).
- client_events at-rest surface minimized (credential-shape denial under any
  key, structured route, no query strings) (PR #888).
- Client-event temporal boundary: unrepresentable dates rejected at the
  schema boundary with per-event client isolation; timeline renders
  `occurredAt` as exact UTC text (PRs #904, #911, ADR-026).
- Client-claimed metadata is labeled unverified next to server facts, with
  source badges in the monitoring dialog (PR #902).
- System audit operations carry `metadata.operationId`, separated from HTTP
  `metadata.requestId`; conflicting operation ids are refused (PR #906).
- Refused answer saves emit one structured WARN keyed by the request id
  (PR #892).
- CI is zero-artifact with authenticated pinned-docs fetches (PRs #894,
  #881), and the release workflow enforces README badge ↔ `.release-version`
  agreement (PR #899).

### Fixed

- Audit keyset cursor epoch-µs precision, ending silent row loss; cursor
  path resets on client error retry (PR #887).
- Role-assignment 404s satisfy the declared error envelope instead of
  degrading to 500 (PR #909).
- candidate.import audit targets name a real entity when the import log
  write fails (PR #910).
- MathLive virtual keyboard no longer buries the formula dialog (PR #883);
  coverage-lane timing races fixed at their proven layers (PR #859).

### Security

- client_events persistence denies credential-shaped values regardless of
  key name and no longer persists raw query strings (PR #888).
- The production request-id header is untrusted by construction (PR #902,
  boot guard; PR #912, `requestIdHeader: false`).

### Deployment / operations

- Migration `0046` is the only schema change: additive `event_id` column +
  unique `(organization_id, user_id, event_id)` index; legacy rows and
  key-less clients stay outside the constraint.
- New alert contract entries for persistent tick-level throw runs and
  persistent business failures in `docs/operations/active-alerting.md`
  (PRs #896, #884); save-failure evidence procedure in
  `docs/operations/save-failure-evidence.md` (PR #892).

### Internal / infrastructure

- ADR-024, ADR-025 and ADR-026 accepted and recorded (PRs #896, #913, #914).
- Naming cleanup retired phase-era and RBAC-migration-era vocabulary in
  production code, tests and tools (PRs #915, #916).
- Zero-artifact CI; flake registry closeouts (#878 registration) (PRs #894,
  #879).

## Known limitations

- **ADR-024 sampled-state contract boundaries.** The tick-failure counter is
  strictly consecutive: high-duty-cycle intermittent throws (3 throws, 1
  clean tick, repeating) never escalate; a finite run can be missed at any
  scanner/monitor ratio (the sample window is part of the contract; no
  "all finite runs reported" claim is made). The #885 fault-injection study
  used a fake database — real PostgreSQL faults, operator delivery and
  statistical miss/false-positive rates were not measured.
- **Stale `business_failure` coexistence (#895, documented residual).**
  During a tick-throw run the business-failure counter is frozen by design
  (#862), so a stale `operability.business_failure/failing` can coexist with
  a truthful `tick_failure/failing`; ADR-024 deliberately does not repair
  this and does not emit a false business recovery.
- **Throw counters are process-local.** The ADR-024 tick-throw counters are
  not projected by `/api/system/diagnostics`; only the #884/#893
  business-failure run-length counters (`consecutiveFailedTicks`) are. The
  client-event retention loop has the same settle/freeze shape but no
  `tick_failure` leg (daily cadence; evidence boundary #544): a throw run
  there remains visible only in per-pass ERROR logs.
- **UUIDv4 uniqueness is probabilistic.** ADR-025 relies on UUIDv4 collision
  improbability rather than a boot registry or central allocator; no
  cross-process uniqueness proof stronger than the pinned cross-process
  generation tests is claimed.
- **No durability/recovery claims.** #813/#828/#827 (answer-durability
  budgets, host/DR continuity) remain open; nothing in this release changes
  the recovery guarantees stated in v0.0.11.
- **Campaign #800 is not finished.** This is the first merged wave; deferred
  decision gates and later phases remain open under the parent issue.
- The flake registry (`docs/standards/test-flakes.md`) still carries open
  registrations (e.g. the #878 E2E geometry flake); both release-relevant
  CI lanes are green on their heads.

## Upgrade notes

- **Read §2 of
  [`docs/deployment/upgrade-and-uninstall.md`](../deployment/upgrade-and-uninstall.md)
  first.** The upgrade is the existing paired-image procedure: deploy
  `ghcr.io/jnhu76/exam:v0.0.12` **and**
  `ghcr.io/jnhu76/exam-web:v0.0.12` together (`init-production-env`
  rewrites `EXAM_IMAGE`/`EXAM_WEB_IMAGE` from `.release-version`; no
  `latest` tag is published). Take the mandatory pre-upgrade backup
  (runbook §15) — it is also the rollback material (§2.5).
- **Migration `0046`** is additive (new nullable `event_id` column + unique
  index treating NULLs as distinct) and applies with no gate; senders that
  do not yet send the key keep working unchanged. The dedup window equals
  row existence under the existing 30-day retention horizon.
- **Request-id format change (ADR-025).** Log/alert tooling that pattern-
  matches Fastify's `req-<base36>` ids must accept UUIDv4. Any client that
  previously set a request-id header in production no longer influences the
  server request id.
- **API surface growth (additive).** Diagnostics gains failure counters and
  `consecutiveFailedTicks`; client-event upload accepts an optional idempotency
  key; a read-only receipt-summary endpoint is added; the audit keyset cursor
  is versioned (v3, epoch-µs) and the client resets the cursor path on error
  retry. Clients that strictly validate these schemas must accept the new
  optional fields.
- **Rollback (§2.5).** Migrations remain forward-only: rollback = restore the
  pre-upgrade database backup plus redeploy the previous image pair. Beware
  the canonical-pin auto-revert on the next `init-production-env` run — pin
  by digest or edit after (§2.5).
- **Version skipping** stays supported by the migration journal replaying
  any backlog in order.
