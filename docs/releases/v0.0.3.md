# Exam v0.0.3

## Why this release exists

`v0.0.3` is the first Exam release where the product baseline and the
public repository surface are aligned for external evaluation.

Since `v0.0.2`, Exam has gained scoped Teacher@Course and Grader@Exam
authority, a complete staff identity lifecycle, permission/audit visibility,
a Plain/Rich WYSIWYG content model, and product-visible `deadline` and
`untimed` timing modes. Deployment and configuration were also simplified:
email delivery now runs in-process instead of requiring a second Exam
container, and runtime settings are converged behind one semantic settings
model.

The repository itself is now easier to approach as a real self-hosted product:
the README is a focused landing page, installation/deployment/operations/
development responsibilities are separated, current authority is separated
from historical evidence, the project carries a standard AGPL-3.0 license,
and the main README/install/development entry guides have Simplified Chinese
versions.

This is still a **pre-1.0** release. It is a credible public-facing baseline,
not a claim that every roadmap item is complete. In particular, the
synchronized `timed_sync` mode has a frozen semantic contract and a latent
kernel, but is not product-activated in this release.

## Problems solved

- **Staff authorization was too broad.** Teachers and Graders are now bound
  to explicitly assigned courses/exams (`capability × assignment`). Lists are
  filtered in SQL before pagination/count, out-of-scope direct-ID probes fold
  into the canonical 404, and revocation takes effect on the next request
  (#286, #296).
- **Staff account lifecycle was incomplete.** Admin-driven invitation, email
  password reset, activation/deactivation hardening, single-use token
  semantics, rate limiting, and audited identity transitions now work end to
  end (#297).
- **Authorization and audit facts were difficult to inspect.** Admins now have
  permission-registry/effective-authority visibility plus bounded audit search
  and CSV export (#298).
- **Exam content was effectively plain text.** The Plain/Rich content protocol
  now supports bounded structured content, WYSIWYG authoring, formulas,
  tables, and code while keeping the read path lightweight and freezing rich
  content into attempt snapshots (#301).
- **Timing policy was too narrow.** `deadline` and `untimed` are now real
  authorable/takable modes, sharing the existing server-authoritative engine.
  The deadline kernel is null-safe, and the admin UI correctly projects
  nullable timing fields (#291 Phase A, #387/#388/#390).
- **A cross-policy start could create an impossible candidate completion
  window.** New attempts are rejected when the effective deadline leaves no
  reachable manual-submit instant after `minSubmitAfterStartMinutes` (#395).
- **Email delivery required an extra runtime process.** Delivery now runs
  in-process while preserving the durable outbox, retry/lease/crash-recovery
  semantics. The shutdown budget and Compose/runtime email configuration were
  hardened after the convergence (#320, #351, #368).
- **The repository looked like an internal engineering workspace rather than a
  consumable project.** The public README/install/dev surface was rebuilt from
  code reality, documentation authority/history were separated, and Chinese
  entry guides were added (#398, #399, #400).
- **Evidence and verifier maintenance was accumulating.** Recovery/rich-content
  test evidence was reduced, obsolete authorization/script surfaces were
  removed, UI scan roots were centralized, and verifier wiring gained a
  meta-guard (#359/#361/#362/#382/#384/#385/#386).

## Notable changes

### Added

- Scoped Teacher@Course and Grader@Exam assignment models with Admin assignment
  APIs/UI and server-side SQL scope filtering (#286, #296).
- Staff invitation, email password reset, and hardened account lifecycle
  (#297).
- Permission registry, effective-authority visibility, and bounded audit
  search/export (#298).
- Plain/Rich content authority with WYSIWYG authoring, formulas, tables, code,
  lightweight rendering, and snapshot-frozen rich content (#301).
- Product-visible `deadline` and `untimed` timing modes (#291 Phase A).
- Latent synchronized-timing kernel and `sync_started_at` persistence
  (#291 Phase B1 / #392).
- Standard AGPL-3.0 licensing, focused contribution/install/development entry
  docs, and Simplified Chinese public entry guides (#398, #400).

### Changed

- Email delivery runs in-process; the separate `email-worker` Compose service
  is removed (#320).
- Email shutdown and SMTP/TLS/timeout environment forwarding are explicitly
  bounded and guarded (#351, #368).
- Application configuration uses a semantic settings authority rather than
  scattered profile/env interpretations (#372).
- Documentation is organized by current authority/guidance versus historical
  evidence; live contracts no longer compete with archived closeouts (#399).
- The repository README is a concise product landing page rather than a combined
  install/deploy/ops/dev manual (#398).

### Fixed

- New attempts cannot enter a state with no reachable candidate manual-submit
  window before their effective deadline (#395).
- Admin exam detail correctly renders nullable timing modes (#389).
- No-deadline paths use null-safe deadline authority (#387).
- Invitation concurrency tests accept both valid race outcomes without hiding a
  real duplicate-invite defect (#381).
- Deployment email environment wiring and bounded shutdown semantics match the
  documented/runtime contract (#351, #368).

### Removed

- Dedicated `email-worker` Compose service (#320).
- `rebuild-all.sh`, which duplicated workspace build-order authority (#382).
- Unused attempt time-extend permission and obsolete shadow authorization mode
  (#363, #366).
- Roughly 1,900 lines of duplicated/visual/over-minimized recovery, incident,
  and rich-content test evidence (#359/#361/#362).

### Security

- Teacher and Grader access is resource-scoped rather than organization-wide
  for their activated workflows (#286, #296).
- Invitation/reset tokens are single-use and identity flows are rate-limited and
  audited; account deactivation participates in credential revocation (#297).
- Permission/audit visibility remains capability-gated and export is bounded
  (#298).

### Deployment / operations

- Reference topology is `app` + `db` with optional Redis; email delivery runs
  inside `app` rather than a second Exam service.
- Six forward-only migrations (0036–0041) are added and are applied
  automatically by the normal entrypoint migration journal.
- **v0.0.2 → v0.0.3 has one required topology-cleanup step:** use
  `docker compose --env-file .env.deploy up -d --remove-orphans` after pulling
  the new image so the removed v0.0.2 `email-worker` container cannot remain
  running beside the new in-process loop.

### Internal / infrastructure

- Semantic settings replace scattered configuration interpretation (#372).
- Recovery/content test evidence was reduced while stronger authority/projection
  assertions were retained (#359/#361/#362).
- UI scan roots and verifier-to-gate wiring now have single-source guards
  (#384/#385/#386).

## Verification

Release membership was audited by ancestry from published tag `v0.0.2`
(`6e949e517b0b734a184209c2ca2aaa9184f9c82a`) through current `master`
(`31eb730b93a45c611b79d66b54809dbe3dad8637`) before the release-metadata
commit. This includes PRs #398, #399, and #400; issue close dates were not used
as release-membership evidence.

The release-preparation PR is metadata-only: `.release-version`, `CHANGELOG.md`,
and this version-specific release record. Before merge it must have the normal
repository final-head gates green, including static checks, build, coverage,
E2E shards, and the deployment fresh-install gate. Older-head CI is not release
evidence.

After merge to `master`, `.github/workflows/release.yml` validates the release
contract on the exact merge SHA, creates/verifies the immutable `v0.0.3` tag,
creates the GitHub Release from this file, and publishes
`ghcr.io/jnhu76/exam:v0.0.3` plus the `sha-*` alias. Publication closeout must
verify tag target, workflow success, image digest, and pullability.

## Known limitations

- **`timed_sync` is not product-activated.** The semantic contract and latent
  kernel exist, but the mode cannot be authored or taken. Phase B2 remains
  under #291.
- **No durable admission queue.** High-assurance queued admission is separate
  roadmap work.
- **Single-node, single-tenant deployment only.** One deployment represents one
  organization; multi-instance/multi-tenant platformization is later work.
- **Rich-content asset upload is not included.** The content protocol is
  asset-ready, but a canonical image/file Asset authority is separate work.
- **Published images are linux/amd64 only.** Other architectures use the
  documented source-build path.
- **Pre-1.0 baseline.** Generic-product and high-assurance roadmap work continues
  under Issue #333.

## Upgrade notes

`v0.0.2 → v0.0.3` introduces six forward-only migrations (0036–0041):
Teacher↔Course assignments, Grader↔Exam assignments, identity lifecycle tokens,
rich-content slots, Phase A timing-mode schema changes, and the nullable Phase B
`sync_started_at` column. They are applied automatically and idempotently by the
entrypoint migration journal; there is no manual SQL/backfill and no PostgreSQL
major-version change.

Take the normal mandatory pre-upgrade database backup, then:

```bash
git pull
node scripts/generate-env.mjs
docker compose --env-file .env.deploy pull
docker compose --env-file .env.deploy up -d --remove-orphans
```

The final `--remove-orphans` is **required for this transition** because v0.0.2
contained a dedicated `email-worker` Compose service and v0.0.3 removed it. A
plain `up -d` can leave that old container running while v0.0.3 also runs the
outbox loop inside `app`. If the old stack was already taken fully down, the flag
is harmless and should still be used.

After upgrade, verify `app` and `db` are healthy (plus Redis only if that profile
is enabled) and confirm no old `email-worker` container remains.

Existing `.env.deploy` files remain valid: newly forwarded email settings have
runtime-equivalent defaults. No intermediate release is required.

Rollback remains forward-only: restore the pre-upgrade database backup, return
to the v0.0.2 checkout/Compose topology, and redeploy the v0.0.2 image. Do not
run the old binary against a database after v0.0.3 migrations have been applied.
