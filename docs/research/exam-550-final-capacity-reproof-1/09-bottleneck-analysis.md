## Method: separating pool wait from query execution

The env-gated research instrumentation wraps `sql.unsafe` — the single funnel every Drizzle
statement passes through — and counts statements currently inside the funnel (`inFlight`) plus
durations. A statement is inside the funnel from dispatch until result, which includes time
awaiting a pool slot. Independently, a 200 ms sampler records `pg_stat_activity` state counts
(`active` = executing server-side). Therefore:

- **pool-queue depth proxy** = funnel in-flight − server-side active (statements waiting for a
  slot);
- **pool saturation** = fraction of research snapshots with in-flight ≥ pool max (10);
- if latency grows while both proxies stay ~0, the cost is query execution or app CPU; if the
  saturation fraction → 1 and queue depth grows with N, the pool is the bottleneck.

This decomposition is measurement, not inference; the wrapper adds the funnel counter around the
existing drizzle path without changing semantics (and is default-OFF — `CAPACITY_RESEARCH=1`).

Row-lock waits on the attempt row (EA update protocol) appear in every write burst but never
dominate: the latency growth tracks queue depth (pool), not lock-wait counts.

## Why these are the bottlenecks (root causes)

1. **Login**: argon2id is intentionally memory-hard; the API delegates hashing to the libuv
   threadpool. 20 concurrent logins ≈ 9 cores of hashing; a simultaneous N-candidate login burst
   is therefore CPU-serialized by design. This is the security parameter working as specified —
   the correct lever if operators need faster logins is more CPU, not weaker hashing.
2. **Submit/grading**: each submit runs a grading transaction through pool max=10
   (#554 KEEP_CURRENT_ARCHITECTURE: PostgreSQL sole authority, no MQ/fanout). With N concurrent
   submissions, queue depth ≈ N − 10 and each transaction costs tens of ms server-side, so p99
   grows ≈ linearly in N (≈ 33 ms/queue-slot at S200). The pool setting is the frozen canonical
   configuration; this campaign measures its cost and does not tune it.
3. **Steady health**: at the measured traffic law (save ~5 s ± 2, heartbeat ~15 s ± 5 per
   candidate), even S200 keeps the pool essentially unsaturated — the envelope's steady-state
   headroom is large.
