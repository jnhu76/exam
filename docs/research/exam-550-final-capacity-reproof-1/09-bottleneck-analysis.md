## Method: what the corrective (neutral) instrumentation can and cannot decompose

MEASUREMENT NEUTRALITY (EXAM-550-CORRECTIVE-1) forbids observing a lazy postgres.js Query's
completion — attaching then/catch/finally (including via `Promise.resolve(thenable)`) SUBMITS
the query for execution. The superseded pre-corrective wrapper did exactly that; its funnel
in-flight/duration numbers (and the "pool wait proxy = in-flight − active" derivation) are
SUPERSEDED, because the observation itself changed submission timing and ordering.

The corrective decomposition therefore uses only neutral sources:

- **statement ARRIVAL counts** at the drizzle→postgres.js funnel (synchronous counter; the
  returned Query is never touched);
- **server-side execution truth**: `pg_stat_activity` state counts at 200 ms (active +
  idle-in-transaction = sessions executing server-side; ≥ pool max ⇒ the pool is the
  bottleneck), lock-wait counts, and — for admission waves — the API's own pino request logs
  (arrival→completion sojourn);
- **process/host evidence**: API CPU and event-loop-delay histogram, RSS, host load/mem, PG
  container CPU.

Derivation law: if client latency grows while pgActive stays ≪ pool max and API CPU is low,
the wait is NOT pool and NOT DB — classify accordingly; if pgActive pins at the pool ceiling
(satFrac → 1) and latency grows with N, the pool is the bottleneck. Every corrective run's
`pool-analysis.json` also stamps the measured topology (`appMode: production`,
`rateLimit.enabled: true`, Redis `optional`/`ready`), so a bottleneck classification can never
be attributed to a topology that was not measured.

| SUBMIT_BURST | **Pool queueing over grading transactions + EA row locks (secondary)** | pgActive pinned at the ceiling (satFrac ≈ 0.85–0.92 from S50 up); DB CPU ≤ 77% → the DB is NOT CPU-bound; lockWaits present but bounded (≤ 9 samples per burst) — the latency tracks the queue, not the locks. |

Row-lock waits on the attempt row (EA update protocol) appear in every write burst but never
dominate: the latency growth tracks pool occupancy, not lock-wait counts.

## Why these are the bottlenecks (root causes)

1. **Login**: argon2id is intentionally memory-hard; the API delegates hashing to the libuv
   threadpool. 20 concurrent logins ≈ 9 cores of hashing; a simultaneous N-candidate login burst
   is therefore CPU-serialized by design. This is the security parameter working as specified —
   the correct lever if operators need faster logins is more CPU, not weaker hashing. The
   production limiter (Redis-backed, one INCR per request) adds no measurable share: login p99
   changed by ≈ ±2% versus the limiter-off superseded runs at the same scale.
2. **Submit/grading**: each submit runs a grading transaction through pool max=10
   (#554 KEEP_CURRENT_ARCHITECTURE: PostgreSQL sole authority, no MQ/fanout). With N concurrent
   submissions the pool fills (pgActive → 10) and each transaction costs tens of ms server-side,
   so p99 grows ≈ linearly in N (S200 p99 ≈ 5.2 s corrective). The pool setting is the frozen
   canonical configuration; this campaign measures its cost and does not tune it.
3. **Steady health**: at the measured traffic law (save ~5 s ± 2, heartbeat ~15 s ± 5 per
   candidate), even S200 keeps the pool essentially unsaturated — the envelope's steady-state
   headroom is large.
4. **What the corrective change did to the envelope**: removing the eager-execution wrapper
   TIGHTENED every steady-state tail (its per-statement eager submission perturbed pool
   acquisition timing); running the production limiter did NOT introduce 429s or visible
   latency at any phase (per-IP budgets are never approached with distinct identities).

## Event-loop sanity

`monitorEventLoopDelay` (1 ms resolution) runs inside the API research snapshot; per-phase p50/p90
land in each run's `pool.jsonl` `source:"research"` snapshots (`snapshot.process.eventLoop`).
No phase shows event-loop saturation
comparable to the latency tails (max observed p90 ≈ 1.7 ms) — consistent with the
classification above (CPU bursts at login, pool queueing at submit; the single Node process is
not the serialization point).
